# AGENTS.md

How humans and AI coding agents work in this repository. This file is authoritative for
conventions, guardrails and how to verify a change. Claude Code reads it through `CLAUDE.md`;
Codex, Copilot and other agents read it directly.

If something here feels strict, that is on purpose: the repo is built to fail early, loudly and
correctly.

---

## Orientation

- **What it is:** a personal recipe site. Sanity Studio (`apps/cms`) for content, Next.js App Router
  (`apps/website`) for rendering, types generated into `packages/sanity-types`. pnpm monorepo, Node 22.
- **Read next, as needed:**
  - [`README.md`](./README.md): setup, commands, environment variables
  - [`ARCHITECTURE.md`](./ARCHITECTURE.md): folder layout, content flow, caching, routes
  - [`docs/content-model.md`](./docs/content-model.md): Sanity types and fields
  - [`docs/deployment.md`](./docs/deployment.md): Vercel, Studio, webhook, CI, secrets

## Commands

```bash
corepack enable && pnpm install   # setup (Node 22)
pnpm typegen                      # regenerate Sanity types; run after any schema change
pnpm ci:verify                    # what CI's Verify job runs: typegen + biome check + tsc (both apps) + tests
pnpm test                         # unit tests for website helpers (node:test through tsx)
pnpm build                        # full build of Studio and website (needs apps/website/.env)
pnpm build:website                # website only
pnpm typecheck:website            # fast type check while iterating
pnpm -w exec biome check --write <paths>   # format and lint specific files
```

`pnpm build` and `pnpm dev:website` need a valid `apps/website/.env` (copy `.env.example`). Without
one, `pnpm ci:verify` still works for schema, lint and type checks.

## Definition of done

A change is done when all of these hold:

1. `pnpm ci:verify` passes.
2. `pnpm build` passes if you touched the schema, a query, a route, `next.config.mjs` or env handling.
   For changes to pages, images or styles, check the Lighthouse job on the pull request too: it fails
   below 0.85 performance or 1.0 accessibility (see `docs/deployment.md`).
3. Docs match the code: update `README.md`, `ARCHITECTURE.md`, `docs/` or this file in the same
   change when you add a command, env var, route, content type or convention.
4. The commit message passes commitlint (see [Commits](#commits)).

CI is the arbiter. Never weaken a check to get green: fix the schema, the types or the code.

## Core rules

### Schema is the source of truth

- Sanity types come only from `@ryan-bakes/sanity-types` (generated by `pnpm typegen`).
- Never hand-write, copy or "mirror" a Sanity document or object shape in the website.
- If generated types and the UI disagree, fix the schema or handle the `undefined`.
- No `sanity-codegen`, no `SanityKeyed`, no ad-hoc reference types. Use TypeGen's generated
  reference types; add `_key` only where arrays require it (`@t/keyed`).

### Optional means optional

TypeGen marks every field optional unless the schema requires it, and drafts can miss required
fields anyway. UI code must guard, fall back, or skip rendering. No non-null assertions (`!`) and no
`as` casts to paper over a missing field.

### Build order

Schema extract, then TypeGen, then website build. Any new script or workflow must keep that order.

### Data fetching

- All GROQ lives in `apps/website/queries`, one default-exported function per file, tagged with
  the `groq` template tag from `@shared/lib/sanity`.
- Page content goes in `queries/live/` and uses `sanityFetch` with cache `tags`. Build-time lists for
  `generateStaticParams` go in `queries/static/`.
- New cache tags must be revalidated by `app/api/revalidate/route.ts`; extend its map in the same
  change if needed.
- Data fetching happens in server components only. Server modules import `"server-only"`.

### Portable Text and images

- Render all Portable Text through `@components/ui/portable-text`. It accepts
  `TypedObject | TypedObject[] | undefined`; callers still guard.
- Sanity images are `ImageWithAlt | undefined` (or `InlineImage`). Check `.asset` before use.
- Render Sanity images with `@components/ui/image` (Sanity CDN `srcset`, crop and hotspot applied).
  When you need a plain URL (Open Graph, metadata), use `urlForImage` or `socialImageUrl` from
  `@shared/lib/image`. Don't route Sanity images through Vercel's image optimizer.

### Environment

- Read env only through `clientEnv` (`@shared/config/env.client`) or `serverEnv`
  (`@shared/config/env.server`), never `process.env` directly in app code.
- New variables follow the checklist in `docs/deployment.md`.

## Code conventions

### TypeScript

- Strict mode with `exactOptionalPropertyTypes: true`. Do not loosen `tsconfig`.
  - An optional prop that may receive `undefined` explicitly is typed `prop?: T | undefined`.
  - Otherwise omit the key, e.g. with a conditional spread: `...(url ? { url } : {})`.
- No `any`. Prefer narrowing (type guards, `in`, `typeof`) over assertions.
- Component props are `type Props = Readonly<{ ... }>`, not `interface`.
- Throw with `throwError` or `throwTypedError` from `@helpers/throw-error` in the website.
- Use the path aliases (`@components/*`, `@queries/*`, ...) instead of long relative imports.

### Braces, always

Every `if`, `else if`, `else`, `for` and `while` body uses braces, even for one statement:

```ts
// yes
if (!slug) {
	return notFound();
}

// no
if (!slug) return notFound();
```

### Zod v4

The website uses Zod 4. Write the current API, not Zod 3 habits:

- String formats are top-level: `z.url()`, `z.email()`, `z.uuid()`, not `z.string().url()`.
- Customize errors with `{ error: "..." }`, not `{ message: "..." }`.
- `z.strictObject()` and `z.looseObject()` instead of `.strict()` and `.passthrough()`.
- `z.record()` takes both a key and a value schema.

### React and Next.js

- App Router only. Every page defines `generateMetadata` and returns `buildPageMetadata` from
  `@helpers/page-metadata` (with `getSiteInfo` from `@shared/lib/site-info`). It sets the canonical
  URL, description, robots and full Open Graph and Twitter objects. Next.js replaces a parent's
  `openGraph` and `twitter` instead of merging them, so don't set those by hand in a page.
- Structured data (JSON-LD) is built by pure functions in `helpers/structured-data/` and rendered with
  `@components/ui/json-ld`. Recipe pages emit `Recipe` and `BreadcrumbList`, tag pages
  `BreadcrumbList`, the home page `WebSite`. Leave a property out when its value is empty; never emit a
  placeholder. Keep the step anchors (`#step-1`, ...) in the steps list, since `HowToStep.url` links to
  them. Cover new builders in a `*.test.ts` next to them.
- Server components by default. Add `"use client"` only for real interactivity, as a small leaf.
- Route-only components go in `app/<route>/features/<feature>/index.tsx`; reusable ones in
  `components/ui` (small) or `components/features` (sections).
- Styles are CSS Modules next to the component (`name.module.css`) using tokens from
  `styles/variables.css`: the spacing scale (`--space-1` to `--space-7`), the type scale
  (`--font-size-*`), `--font-serif` and `--font-sans`, `--surface`, `--border`, `--radius` and the
  card shadows. Prefer a token to a one-off value. Fonts load only through `next/font` in
  `app/layout.tsx`; don't add a font `<link>` or `@import`. Data tables use the shared `@components/ui/table/table.module.css`.
- Keep text contrast at 4.5:1 or better (`--text-muted` for secondary text, not `--neutral-600`;
  `--secondary-dark` for accent lines and rings on light backgrounds, `--secondary-on-primary` on
  the enamel blue) and
  keep visible focus rings (`--focus-outline-*`). The Lighthouse check fails below 100 accessibility.

### Sanity Studio

- Use `defineType`, `defineField` and `defineArrayMember`. Give fields a `title` and a helpful
  `description`; put validation in the schema.
- Register new types in `apps/cms/schemas/index.ts`. Singletons also need an entry in `singletons.ts`
  and a list item in `structure.ts`.
- Put fields in the document's `groups` (tabs) and give list types a `preview` that reads well.
- Validation that catches likely mistakes in existing content is a `.warning()`, not an error, so old
  documents still publish. Shared validators live in `apps/cms/helpers/validation.ts`.
- Schema changes must keep existing data valid: no field renames or type changes without a
  migration plan. Field titles, descriptions, groups and previews are safe to change.
- Custom inputs use `@sanity/ui`. `useFormValue` takes a path from the document root.

### Formatting

Biome formats and lints everything (tabs, width 120). Do not add Prettier or ESLint config.
`.editorconfig` covers file types Biome does not.

### GitHub Actions

- Use `actions/checkout@v5` and `actions/setup-node@v6`, Node `22`, pnpm through Corepack, and
  `pnpm install --frozen-lockfile`. Reuse the `.github/actions/setup` composite action.
- Keep Verify before Build and keep fork PRs safe (no secrets for forks).
- Don't rename the Verify or Build jobs or add a path filter to `ci.yml`: the `main` ruleset requires
  those checks by name.
- Give every workflow `permissions: contents: read` by default, and pass untrusted values (PR
  titles, inputs) to scripts through `env:`, never `${{ }}` inside `run:`.
- Avoid third-party actions unless clearly justified; never hardcode env values in workflows.

## Commits

Conventional Commits, enforced by commitlint (`commitlint.config.mjs`):

- Types: `build`, `add`, `feature`, `bug`, `chore`, `docs`, `refactor`, `revert`, `test`, `style`,
  `perf`, `package`.
- Lower-case subject, no trailing period, header and body lines at most 100 characters.
- Add a body that explains what changed and why.

The pre-commit hook runs Biome and `tsc` on staged files. Do not skip hooks with `--no-verify`.

## Guardrails

Do not, unless the person you are working for explicitly asks in this task:

- Commit `.env` files or write a secret value anywhere (code, docs, logs, PR text). Names only.
- Edit generated files: `packages/sanity-types/sanity.types.ts`, `apps/cms/schema.json`.
- Edit `pnpm-lock.yaml` by hand, or add, remove or upgrade dependencies as a side effect.
- Edit the vendored agent skills in `.agents/skills`, `.claude/skills` or `.copilot/skills`
  (they are third-party and tracked in `skills-lock.json`).
- Deploy the Studio, trigger a production deployment, or create, edit, publish or delete Sanity
  content. Code changes go through pull requests; content changes happen in the Studio.
- Disable lint rules, loosen `tsconfig`, skip CI steps or mark tests as skipped.
- Merge pull requests or enable auto-merge.

When unsure, choose the most explicit and safest option, and say what you assumed.
